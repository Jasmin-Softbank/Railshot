## 실행한 사전 확인

현재 브랜치·clean working tree(미커밋 변경 없는 상태)·원격 주소를 확인하고 git fetch origin을 실행했습니다. integration 비교에서 Cilium 최초 control-plane label(서버 역할 표시) 대기 수정, operations build agent(빌드 전용 실행 노드) 프로필, Ansible 연결 변경을 발견했습니다. 사용자에게 먼저 설명한 뒤 현재 feature 브랜치에서만 일반 merge를 실행했습니다. 충돌은 없었습니다. 이 작업에서 새 기능을 작성하거나 해당 팀 코드를 편집하지 않았습니다.

gcloud --version을 실제 실행했으며 command not found를 확인했습니다. PATH 및 다음 기본 위치의 존재 여부만 확인했습니다: 사용자 google-cloud-sdk, ~/.config/gcloud, Homebrew share/Caskroom, /usr/local/share/google-cloud-sdk. 모두 발견하지 못했습니다. CLOUDSDK_CONFIG, GOOGLE_APPLICATION_CREDENTIALS, CLOUDSDK_AUTH_CREDENTIAL_FILE_OVERRIDE, CLOUDSDK_AUTH_ACCESS_TOKEN, GOOGLE_CLOUD_PROJECT 환경변수도 **설정 여부만** 검사했으며 모두 미설정입니다. 이는 임의 경로에 인증 자료가 절대 없다는 증명은 아닙니다.

사용자에게 기존 승인된 접속 경로·전용 시험 노드가 있는지 확인했고, **“현재 준비된 인증·시험 노드가 없습니다”**라는 답변을 받았습니다. 시스템 설정·SDK 설치·GCP 로그인은 수행하지 않았습니다. gcloud auth list/config list/projects describe/compute instances list는 실행할 도구가 없어 미실행입니다.

[팀의 기존 클라우드 기록](../../../../docs/integration/cloud-e2e-progress.md)은 GCP 앱, 기존 K3s/Cilium, IAP(권한 확인을 거치는 접속 경로) 사용을 설명합니다. 이것은 다른 담당자의 과거 실행 기록이며 이번 controller(Mac에서 명령을 실행하는 환경)의 인증·대상 소유권 검증을 대체하지 않습니다. 다른 사용자의 관리자 자료나 비밀 파일을 탐색하지 않았습니다.

## 실제 시험을 재개할 조건

1. 프로젝트 railshot-poc-20261001, region asia-northeast3, zone asia-northeast3-a에 대해 기존 인증·조회·접속 방법을 준비해야 합니다. 토큰·개인 키·credential JSON은 Git이나 채팅으로 공유하지 않습니다.
2. 이름·label·팀의 명시적 확인으로 Runtime 전용 시험 노드를 확인해야 합니다. 기존 앱 노드의 중단·초기화·재사용을 가정하지 않습니다. VM 생성·시작·방화벽 변경은 이번 Runtime 작업에서 수행하지 않습니다.
3. 원격 read-only preflight(변경 없는 사전 검사)로 OS/CPU/root 권한/디스크/메모리/기존 K3s·CNI·앱을 확인합니다. 공유 자원·관리되지 않은 클러스터가 있으면 실행을 중단합니다.
4. 안전한 대상 확정 후 기존 gcp fixture를 기반으로 고유 environment_id·namespace(앱 격리 공간)를 선택하고, NodePort(노드의 앱 접속 포트)가 사용 중인지 확인합니다. 최초 설치에는 기존 입력 runtime.timeout_seconds: 600을 사용할 수 있으며 기본 정책은 바꾸지 않습니다.
5. 대상 Linux에서 기존 deploy.sh --mode online --input <검증된-GCP-입력>과 verify.sh --input <같은-입력>을 실행합니다. 내부 DNS→Service→HTTP, node-local NodePort, 실제 JSON을 수집합니다. amd64 대상이면 이번 우선 경로는 online이며 arm64 bundle을 전송하지 않습니다.
6. 외부 IP·기존 방화벽으로 접근 가능할 때만 Mac에서 외부 HTTP를 검사합니다. node-local 성공/외부 접근 제한은 Runtime 결함과 구분합니다. 소유권이 명확한 앱 제거만 별도로 판단하며 전체 cleanup은 기본 실행하지 않습니다.
