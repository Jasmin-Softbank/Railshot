## 전체 init가 현재 차단되는 조건

현재 `main.initialize()`는 등록 → WireGuard → OpenStack 순서이며 등록 단계를 생략하는 운영 옵션이 없습니다. 등록 서버가 없으면 OpenStack 구현까지 도달하지 못합니다.

전체 실행에는 다음이 모두 필요합니다.

- 실제 HTTPS `POST /v1/enrollments`: 일회용 키 검증과 동일 request_id/공개키의 응답 복구.
- 실제 WireGuard 상대 서버, 공개키, 노드별 주소, 도달 가능한 UDP 접속점, 서버의 노드 등록.
- /32 또는 /128 호스트 경로 안의 실제 HTTPS 점검 주소와 해당 IP를 인증하는 인증서.

가짜 등록 응답 파일을 심거나 함수를 바꾸면 전체 실환경 검증으로 인정하지 않습니다. 서버가 없는 상태에서는 아래 OpenStack 모듈 직접 호출만 별도 실환경 검증으로 수행할 수 있습니다. 이 경우 등록·터널·전체 설치 성공은 계속 미검증입니다.

## 대체 응답 없이 가능한 OpenStack 모듈 검증

### 1. 조회·암호화 저장·진단

실제 고객 자격증명으로 `OpenStackCLI`와 `discover_capabilities`를 호출합니다. 기존 애플리케이션 자격증명을 사용할 경우 이는 전용 계정 생성 흐름의 검증을 포함하지 않습니다. 다음은 관리자 터미널에서 실행할 예시입니다. `PYTHONPATH`는 검증된 소스 기준이며 `/root/jasmin-e2e`는 새로 만든 root 전용 0700 작업 경로입니다.

```sh
# 아래 REPO와 PYTHON은 실제 검증 소스와 준비된 Python 환경의 절대 경로로 지정합니다.
sudo env PYTHONPATH="$REPO/deployment/bootstrap:$REPO" "$PYTHON" /root/jasmin-e2e/query.py
```

실행할 `/root/jasmin-e2e/query.py`의 내용은 다음과 같습니다. 비밀정보를 파일에 기입하지 않습니다.

```python
from getpass import getpass
from pathlib import Path
from client_setup.credentials import CredentialStore
from infrastructure.providers.openstack.cli import OpenStackCLI
from infrastructure.providers.openstack.discovery import discover_capabilities

expected_project = input('확인한 시험 프로젝트 UUID: ').strip()
auth = {
    'auth_url': input('Keystone HTTPS v3 주소: ').strip(),
    'application_credential_id': input('고객 애플리케이션 자격증명 ID: ').strip(),
    'application_credential_secret': getpass('자격증명 비밀값: '),
    'interface': 'public',
}
cli = OpenStackCLI(auth)
token = cli.run(['token', 'issue'])
if token.get('project_id') != expected_project:
    raise SystemExit('프로젝트 불일치: 작업을 중단합니다.')
del token
vault = CredentialStore(Path('/root/jasmin-e2e/credentials'))
vault.save(auth)
report = discover_capabilities(OpenStackCLI(vault.load()))
print({name: item['status'] for name, item in report.get('services', {}).items()})
print('프로젝트 일치 및 실제 조회 수행. 생성 권한은 별도 검증 필요.')
```

`input`과 `getpass`를 사용할 수 있는 상호작용 터미널에서 실행해야 합니다. 제어 터미널이 없는 자동 실행 환경에서 비밀정보 입력을 진행하지 않습니다. 실자료 전체 출력 대신 서비스별 결과와 식별자만 필요한 범위에서 기록합니다.

### 2. 전용 계정 생성 흐름

계정 생성 권한을 가진 관리자가 직접 입력할 수 있을 때만 `configure_identity(config, getpass(...), on_resource=state.record_resource)`를 실제 호출합니다. 설정은 확인한 프로젝트 UUID, 도메인, 역할 UUID와 신규 전용 계정 이름을 사용합니다. 다른 프로젝트나 시스템 범위 권한이 필요한 경우 임의로 권한을 확대하지 않습니다.

성공 시 반환 자격증명을 `CredentialStore.save()`로 저장하고 실제 토큰의 프로젝트를 대조합니다. 부분 실패 시 기록된 계정/역할/자격증명 ID를 보존하며 기존 계정을 자동 인수·암호 재설정하지 않습니다. 관리자 입력이 없으면 이 항목은 미검증으로 남깁니다.

### 3. 접속 기반과 새 가상 머신

먼저 조회 단계의 실제 프로젝트 일치 검사를 통과해야 합니다. `prepare_vm_access(cli, config, Path('/root/jasmin-e2e/access'), on_resource=state.record_resource)`를 호출합니다.

필수 설정은 `network_id`, `ssh_username`(예: ubuntu), 제한된 `ssh_source_cidr`, `resource_prefix=jasmin-bootstrap-e2e-20261002-01`입니다. 함수는 실제 키쌍과 전용 보안그룹을 만들며 가상 머신·라우터·외부 연결 주소는 만들지 않습니다.

반환한 `keypair_name`, `security_group_id`, `network_id`, `cloud_init_path`를 **새 시험 가상 머신 생성 시** 적용합니다. 이어 확인한 시험용 외부 연결 주소를 그 가상 머신의 정확한 포트 식별자에 연결합니다. 기본 보안그룹을 추가로 연결하면 제한 규칙 검증을 왜곡할 수 있으므로 연결된 보안그룹 전체를 확인합니다.

실제 주소를 반환 프로필의 `host`에 넣고, 독립 확인한 known_hosts 파일을 root 소유 0600으로 준비하여 `verify_vm_access(profile, known_hosts_path)`를 호출합니다. 이 함수는 실제 SSH 연결에서 `true` 명령을 실행하고 호스트 키 검증을 강제합니다. `route_status`만 바꾸거나 SSH 접속을 대체하지 않습니다.

### 4. 종료·정리

신규 자원 식별자 목록과 실제 프로젝트를 다시 대조한 뒤 시험 가상 머신, 이번 시험 할당 외부 주소, 신규 보안그룹·키쌍·자격증명·전용 계정을 의존성 순서에 맞게 정리합니다. 고객이 보존을 요청한 시험 자원은 상태와 목적을 명시합니다. 기존 관리 노드와 기존 인프라는 정리 대상이 아닙니다.

## 당시 관측 — 사용자 승인 규칙과 두 노드 SSH 접속 성공

사용자는 이번 시험 보안그룹의 들어오는 TCP 22번 포트 출발지 `0.0.0.0/0` 허용을 승인하고, 해당 설정을 계속 유지하라고 명시했습니다. 실행 담당자는 화면에서 규칙의 존재를 확인했으며 같은 규칙을 중복 생성하지 않았습니다. 규칙은 사용자가 직접 제출한 것으로 보이나, 제출 주체 자체를 확정 기록하지 않습니다. 자동 재축소 또는 제거를 수행하지 않습니다.

## 승인된 후속 검증 범위 — 두 노드 간 작업 지시

사용자는 두 번째 시험 가상 머신에서 작업을 지시하고 첫 번째 가상 머신이 OpenStack CLI로 실행한 뒤 결과를 반환하는 기능을 추가 승인했습니다. `instance.list` 조회 전용 요청, 고객 노드의 로컬 인증정보, SSH 강제 실행 명령을 사용하는 방식입니다. 프로토콜·자동 검증은 `docs/api/job-contract.md`와 `ci/tests/test_agent_jobs.py`로 관리합니다.

이 추가 승인 시점에는 두 가상 머신에서 입출력 대기 비율이 약 99~100%로 관측되어 패키지 설치가 느리지만 진행 중입니다. 실제 OpenStack 인증정보가 준비되지 않아 두 노드 간 실제 조회·결과 반환은 아직 확인하지 못했습니다. 모의 요청 테스트 통과를 실제 클라우드 조회 성공으로 기록하지 않습니다.

## 설치 진행 상태 및 작업 전용 키 준비

해당 기록 시점의 관측에서 패키지 설치는 dpkg 압축 해제 단계 73개 중 27개까지 진행했으며, 입출력 대기 비율은 약 99%입니다. 설치가 진행 중인 상태로, 완료 또는 정상 실행으로 기록하지 않습니다. 다른 사용자 자원이나 승인된 시험 보안그룹 설정을 추가 변경하지 않았습니다.

기존 원격접속 키를 보존하면서 제한된 작업 전용 키를 추가하는 보조 스크립트를 저장소 밖 `/private/tmp/jasmin-bootstrap-e2e-20261002-02/append_restricted_key.py`에 준비했습니다. 아직 실행하지 않았습니다. root 소유 부모 경로·파일 권한·심볼릭 링크·하드링크 검사, 중복 키 확인, 기존 파일의 별도 백업, 교체 직전 변경 감지, 원자적 추가와 기존 내용 보존 확인을 수행하도록 작성했습니다. 파일 잠금은 협조하는 작업 간 잠금이므로 다른 관리자의 동시 수동 수정까지 강제로 막는 장치로 간주하지 않습니다.

## 작업 전용 키 추가 보조 스크립트 격리 검증

실행 권한을 승인받아 두 번째 시험 노드 `10.26.2.171`에서 root로 보조 스크립트를 검증했습니다. 대상은 `/root/jasmin-append-check` 아래 임시 디렉터리의 **가짜 authorized_keys**이며, 실제 `/root/.ssh/authorized_keys`는 읽거나 수정하지 않았습니다. 임시 시험 파일은 검증 종료 시 제거되었습니다.

실제 root 소유권·파일 권한을 적용한 다음 7개 검증이 모두 통과했고 종료 코드는 0입니다.

1. 기존 내용의 바이트 단위 보존과 백업.
2. 같은 제한 키 재등록 시 추가하지 않는 재실행 처리.
3. 동일한 키가 무제한으로 등록된 경우 거부.
4. 심볼릭 링크 대상 거부 및 원본 보존.
5. 하드링크 대상 거부 및 원본 보존.
6. 0600이 아닌 키 파일 권한 거부.
7. 교체 직전 다른 편집을 모의한 경우 변경 감지 및 그 편집 내용 보존.

로컬 결과 파일은 `/private/tmp/jasmin-bootstrap-e2e-20261002-02/append-harness-test-result.json`입니다. 이는 보조 스크립트의 격리 검증이며 실제 작업 키 설치 또는 OpenStack 조회 성공을 의미하지 않습니다. 비협조적 root 동시 수정과의 완전한 원자적 비교·교체를 보장하지 않는 제한도 유지됩니다.
