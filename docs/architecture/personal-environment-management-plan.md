# 개인 배포환경 관리 — 구현 공수 및 작업계획

작성일: 2026-10-03 · 기준 커밋: `abd968be63a2fa39412ed2c6586c3870085bbbb2`

요청하신 기능은 **별도 환경 관리 화면, OpenStack 연결 설치, 등록 환경 선택 배포, 상태 조회, 서비스 삭제 및 클라이언트 제거**를 함께 구현하는 작업입니다. 현재 코드 기준 예상 순수 공수는 **29–44인일**, 통합·환경 차이에 대한 여유를 포함하면 **35–53인일**입니다. 1인일은 개발자 1명이 하루 8시간 작업하는 양이며, 확정 견적이 아닌 소스 검토 기반 추정입니다.

사용자 정정 사항을 반영해 **삭제 대상은 해당 환경에 RailShot으로 배포했던 서비스와 RailShot 관리용 구성요소로 한정**합니다. 고객이 별도로 운영하던 서비스, OpenStack 자체 운영 구성요소, 다른 환경은 삭제하지 않습니다. 가상 머신·볼륨 등 기반 인프라 전체 철거는 이번 범위에 포함하지 않습니다. 사용자 확정 정책에 따라 앱 전용 영구 데이터도 환경 삭제 계획에 포함하고, 실행 시 명시적으로 함께 삭제를 확인합니다. 공유 스토리지·외부 데이터는 제외합니다.

이 문서의 공수 표와 초기 조사 결과는 작업계획 시점의 기록입니다. 이후 사용자는 구현을 승인하고, 로그인 없이 장기 소유자 쿠키·복구키를 사용하며 서비스와 앱 전용 데이터를 함께 삭제하는 정책을 확정했습니다. 현재 구현 규격과 제한은 [개인 환경 API](../api/personal-environments.md)를 참조하세요. 이후 추가 정정으로 설치 완료 기준은 “서버 프로젝트가 고객 OpenStack 클러스터에 OpenStack CLI 명령을 실행할 수 있는 상태”로 확정되었습니다. 관련 VM·K3s·배포 설정은 다른 파트에서 구현·트리거하므로 이 등록 기능에서 새로 구현하지 않습니다. 아래 초기 산정의 런타임 자동 구성 항목은 현재 구현 범위가 아닙니다. 실제 고객 환경 연결·삭제, 병합 및 운영 배포 완료를 뜻하지 않습니다.

## 3. 화면 및 사용자 흐름

### 개인 배포환경 관리

좌측 메뉴의 배포 내역 아래에 구분선과 **개인 배포환경 관리**를 추가합니다. 기존 환경 모니터링은 유지하고, 관리 화면은 개인 환경의 추가·상세·삭제를 담당합니다. 같은 상태 조회 결과를 재사용해 서로 다른 상태를 표시하지 않도록 합니다.

환경 목록은 이름, OpenStack 프로젝트 구분 정보, 연결 상태, 마지막 응답 시각, RailShot 서비스 수를 표시합니다. 목록 없음·조회 실패·설치 중·연결 끊김은 구분합니다. 상세에서는 다음을 제공합니다.

- RailShot으로 배포한 서비스 목록: 이름, 실행 상태, 마지막 배포 시각, 확인된 공개 주소.
- 클라이언트 상태와 버전, 최근 상태 보고, 터널 도달성, OpenStack 인증 상태.
- 수집 가능한 노드의 CPU·메모리·루트 디스크 사용률과 네트워크 송수신량. 반드시 수집 시각과 측정 대상을 함께 표시합니다.
- 등록 진행 재개, 설치 명령 재발급, 환경 삭제 및 실패 단계 확인.

클라이언트 한 대의 메트릭을 OpenStack 프로젝트 전체 사용량으로 표현하지 않습니다. 기존 수집기를 연결하지 않은 노드는 ‘미수집’, 오래된 값은 ‘갱신 지연’으로 표시합니다. 서버가 응답하지 않는 경우 0이나 정상으로 표시하지 않습니다. 화면 활성 상태에서 30초 주기 갱신을 기본안으로 하고, 연결 상태와 지표 신선도 기준은 명세에 고정합니다.

### 신규 등록

1. 환경 이름을 입력해 등록 요청을 만듭니다. 서버는 소유자에 연결된 환경과 짧은 유효기간의 일회용 등록 자격을 발급합니다.
2. 화면에 복사 버튼과 **설치 스크립트 하나를 실행하는 진입점**을 제공합니다. 파일은 한 번만 복사하며, 필요한 패키지와 고정 버전의 클라이언트는 설치기가 내려받습니다. 완전 오프라인 단일 파일 묶음은 기본 범위가 아닙니다.
3. 사용자는 OpenStack 관리망에 접근 가능한 전용 관리 호스트에서 실행합니다. 관리자 권한, 지원 운영체제, 외부 연결 및 프로젝트 접근을 검사합니다.
4. 기존 현장 설정을 사용할 수 있으면 읽고, 없으면 터미널에서 프로젝트·인증정보를 입력받습니다. ‘스크립트 한 번 붙여넣기’가 ‘인증정보 입력도 전혀 필요 없음’을 뜻하지는 않습니다. OpenStack 비밀번호를 웹 화면이나 설치 명령 원문에 넣지 않습니다.
5. 고객 측에서 개인키를 생성하고 공개키만 등록합니다. 서버가 연결 상대와 전용 주소를 배정하고 터널을 구성합니다. 고객 간 사설 주소 중복이 전파되지 않도록 관리 호스트 중심으로 격리합니다.
6. 터널 연결, 고객 작업 응답, OpenStack 조회를 각각 확인합니다. 이후 실제 배포에 필요한 실행환경·권한·관측 연결 준비까지 확인해야 ‘배포 가능’으로 표시합니다.
7. 등록 완료 시 상세로 이동하고, 새 배포에서 진입한 경우 **이 환경으로 배포 계속하기**를 제공합니다.

기존 실행환경이 없는 OpenStack 프로젝트의 경우, 클라이언트 연결만으로 앱 배포가 가능해지는 것은 아닙니다. 지원하는 고정 사양으로 실행환경을 준비하는 경로 또는 기존 K3s 실행환경을 연결하는 경로를 정하고 기존 공급자·설치 코드를 연결해야 합니다. 이 연결 공수는 아래 산정에 포함하되, 임의의 모든 클러스터·운영체제 자동 전환은 포함하지 않습니다.

### 새 배포 화면

사용자의 ‘가장 마지막 드롭다운’ 요구는 **온프레미스 환경 선택 드롭다운의 마지막 항목**으로 해석합니다. 별도의 기존 미완료 등록 드롭다운은 관리 화면으로 옮깁니다.

- ‘인프라 종류’에는 본인에게 등록된 OpenStack 환경 이름을 표시합니다. 예: `연구실 OpenStack`, `개인 테스트 OpenStack`.
- 마지막 항목은 항상 **신규 OpenStack환경 추가**입니다. 실제 환경 식별자로 사용하지 않습니다.
- 해당 항목을 선택하면 아래에 등록 안내와 **개인 배포환경 관리로 이동** 버튼을 표시하고 배포 제출을 막습니다. 선택 즉시 강제로 이동시키지 않습니다.
- 미등록 상태에는 신규 추가 항목과 안내를 표시합니다. 조회 실패는 미등록으로 오인하지 않도록 재조회 안내를 제공합니다.
- 연결 끊김·설치 미완료 환경은 상태와 함께 표시하되 배포를 막습니다. 삭제 중·삭제 완료 환경은 배포 후보에서 제외합니다. 서버도 동일하게 검증합니다.
- 같은 페이지 내부 화면 이동으로 소스 선택과 앱 이름을 메모리에 유지합니다. 새로고침 뒤 로컬 파일 자동 복원을 약속하거나 파일·자격증명을 브라우저 영구 저장소에 저장하지 않습니다.
- 클라우드의 AWS/GCP 선택은 유지합니다. 이 온프레미스 선택창에서 Proxmox가 보이지 않게 되는 변경은 이번 요구에 포함하며, 다른 경로의 Proxmox 구현은 삭제하지 않습니다.

## 4. 서버·클라이언트 설계안

### 자원과 소유권

개인 환경을 기존 배포 실행 기록인 `environments`와 구분하고, 기존 실행 대상인 `targets`를 확장하는 안을 권장합니다. 외부에 표시할 환경과 그 환경에 속한 앱별 배포 대상을 연결합니다. 저장 항목은 환경 이름·소유자·프로젝트 식별자·등록 세대·클라이언트 공개키·연결 주소·상태·최근 응답·가능한 작업·삭제 작업 식별자입니다.

일회용 등록 자격은 원문 대신 검증값과 만료·사용 상태를 저장합니다. 등록 자격과 지속 접속 자격을 분리하며, 사용 후 같은 등록 자격으로 다른 호스트가 환경을 가져갈 수 없게 합니다. 비밀번호·개인키는 목록과 작업 로그에 포함하지 않습니다.

현재 익명 세션을 그대로 개인 환경의 영구 소유자로 사용하면 쿠키 소실·7일 만료 후 관리권이 사라집니다. 구현 1단계에서 **지속되는 소유자 인증과 계정 복구 방식**을 정해야 합니다. 초기 산정은 외부 로그인 제공자 연결을 가정했으나 사용자 확정으로 변경했습니다. 구현은 별도 장기 HttpOnly 소유자 쿠키와 일회 표시 복구키를 사용합니다. 서버에 해시만 보관하고 복구 시 이전 쿠키와 키를 회전합니다. 자체 회원가입·외부 로그인·조직·결제 시스템은 추가하지 않습니다. 익명 세션만 사용하는 시연판은 장기 개인 관리 기능의 완료로 간주하지 않습니다.

기존 정적 OpenStack 환경은 운영자 소유로 유지합니다. 검증된 관리자가 명시적으로 이전할 때만 개인 소유로 바꾸며, 단순 접속정보 저장 항목인 `connections`를 실제 등록 환경으로 자동 변환하지 않습니다.

### 제안하는 호출 규격

아래 경로는 설계안입니다. 현재 구현된 경로·필드와 구분하며 [제품 호출 규약](../api/conventions.md)에 맞춥니다.

| 경로 | 역할 |
| --- | --- |
| `GET /api/v1/targets?provider=openstack&scope=owned` | 본인 OpenStack 환경 목록. 두 조회 조건은 신규 확장입니다. |
| `POST /api/v1/targets` | 개인 환경 등록 요청을 생성합니다. 기존 운영자 설정을 임의로 덮어쓰지 않습니다. |
| `GET /api/v1/targets/{id}` | 등록 단계·연결 상태·가능한 작업을 조회합니다. |
| `POST /api/v1/targets/{id}/enrollments` | 일회용 등록 자격 발급·재발급. 이전 미사용 자격은 폐기합니다. |
| `POST /api/v1/enrollments/{id}/claims` | 고객 클라이언트가 등록 자격과 공개키를 제시해 등록합니다. 브라우저 로그인과 별도 인증입니다. |
| `POST /api/v1/targets/{id}/heartbeats` | 환경에 묶인 클라이언트 자격으로 최근 응답·기능 상태를 보고합니다. |
| `GET /api/v1/targets/{id}/observations` | 기존 메트릭 조회를 재사용·확장합니다. |
| `GET /api/v1/targets/{id}/applications` | 해당 환경의 RailShot 서비스 목록을 조회합니다. |
| `POST /api/v1/targets/{id}/plans` | 삭제할 서비스·관리 구성요소와 보존할 자원, 차단 사유를 계산합니다. 실제 삭제하지 않습니다. |
| `POST /api/v1/targets/{id}/operations` | 확인된 계획을 기준으로 비동기 삭제를 접수합니다. |
| `GET /api/v1/operations/{id}` | 기존 앱 작업 조회를 환경 작업까지 확장합니다. |

배포 요청은 예를 들어 `deployment_selection: { environment: "onprem", provider: "openstack", target_id: "등록된 환경 식별자" }`를 사용하도록 확장합니다. 현재 선택 요청에 `target_id`가 없으므로 화면뿐 아니라 입력 검사·중복 요청 판별·대상 해석·실행 직전 검증을 함께 바꿉니다. 클라우드의 기존 입력은 유지합니다. 임의 주소·로컬 경로·명령 문자열을 받지 않습니다.

환경 상태는 `pending → installing → connecting → ready`를 기본으로 하며 실패·연결 끊김·삭제 중·확인 필요·삭제 완료를 구분합니다. 터널만 연결된 상태와 앱 배포까지 준비된 상태도 구분합니다. 삭제·등록 세대와 소유권 검사는 직접 대상 지정, 앱 재시작·갱신, 비동기 작업 재개 경로에도 적용합니다.

### WireGuard와 제어 연결

WireGuard는 통신 경로입니다. 앱 배포 권한, OpenStack 작업 권한, 클라이언트 작업 처리는 별도 구성해야 합니다. 기본안은 고객 관리 호스트가 서버로 연결하고, 서버가 터널 안의 제한된 작업 처리기 및 필요한 실행환경 연결만 사용하는 구조입니다. 고객 전체 관리망을 다른 고객에게 노출하거나 임의 셸을 열지 않습니다.

서버 측 연결 상대·주소 배정 상태와 실제 네트워크 설정을 함께 관리하고, 서버 재시작 시 복구·삭제된 연결의 재생성 방지를 구현합니다. 방화벽·중복 사설 주소·경로·패킷 크기 문제는 지원 환경에서 검증합니다. WireGuard의 방화벽 연결 유지 설정은 필요할 때 적용하며, UDP 통신이 차단된 환경은 사전 검사에서 안내합니다. 별도 대체 터널 제품 개발은 기본 범위에 포함하지 않습니다. [WireGuard 공식 시작 안내](https://www.wireguard.com/quickstart/)

OpenStack 인증은 프로젝트 범위로 제한하고 고객 측에 보관하는 방식을 우선 검토합니다. Application Credential은 프로젝트 역할을 위임할 수 있지만 기본 설정에서 다른 Application Credential의 생성·삭제에는 제한이 있으므로, 자동 발급·폐기까지 가능하다고 가정하지 않습니다. 현장 권한으로 가능한 폐기 경로를 먼저 확인합니다. [OpenStack 공식 Application Credentials 안내](https://docs.openstack.org/keystone/latest/user/application_credentials.html)

## 5. 환경 삭제 흐름

### 범위

| 삭제 대상 | 보존 대상 |
| --- | --- |
| 해당 환경에 RailShot이 배포한 서비스와 그 전용 공개 경로·배포 연결 | 고객이 RailShot 외부에서 배포한 서비스 |
| 환경 전용 관측 등록·권한·접속키·터널 연결 상대 | 다른 환경의 수집 설정·키·터널과 공용 관리 서버 |
| RailShot 클라이언트 프로그램·전용 시스템 서비스·전용 로컬 비밀 파일 | OpenStack 자체 구성, 기존 가상 머신·공유 네트워크·기반 클러스터 |
| 서비스와 환경의 활성 등록 | 작업 결과·삭제 증거·감사 이력 |

앱의 전용 영구 데이터는 사용자 승인에 따라 서비스와 함께 삭제합니다. 현재 앱 삭제 실행기는 명시적인 `delete_data` 확인을 요구하며, 지원 스토리지의 삭제 조건까지 검사합니다. **앱 전용 데이터 삭제 승인을 공유 스토리지나 모든 볼륨 삭제 동의로 확대하지 않습니다.** 삭제 계획에서 앱 전용 데이터 영향과 외부 데이터 보존을 구분하고 정책이 정해지지 않았거나 지원되지 않는 경우 차단합니다. 데이터 보존 모드가 필요하면 기존 실행기에 추가 개발이 필요합니다.

### 실행 순서와 실패 처리

1. 환경 소유자 권한을 확인하고 등록 세대·앱 목록·실제 자원 식별자로 삭제 계획을 만듭니다. 다른 소유자의 RailShot 앱이 섞인 기존 공용 환경은 개인 환경 삭제로 처리하지 않습니다.
2. 화면에서 삭제할 서비스, 클라이언트, 데이터 영향과 보존 자원을 확인한 뒤 한 번 실행합니다. 계획 만료 또는 실제 자원 변경 시 다시 계획합니다.
3. 접수와 동시에 환경을 `deleting`으로 저장하고 신규 배포·앱 갱신·재시작을 막습니다. 진행 중 배포는 기존 중단·결과 확인 절차와 연결합니다.
4. 기존 앱 삭제 실행기를 사용해 환경 내 RailShot 서비스를 순차 삭제합니다. 기존 공유 실행기 제약을 존중하며, 환경 작업이 자기 하위 앱 삭제 작업을 차단하지 않도록 부모·하위 작업 관계를 정의합니다.
5. 각 서비스의 실제 삭제를 확인한 뒤 환경 전용 배포·관측·자격 갱신 연결과 권한을 정리합니다. 기존 공용 설정은 해당 항목만 제거합니다.
6. 고객 측 정리 작업이 클라이언트 전용 서비스·실행 파일·키·설정을 정리합니다. 마지막 정리까지 필요한 제어 경로는 유지하며, 호스트 자체를 삭제하지 않습니다.
7. 클라이언트 정리 결과를 기록하고 서버의 연결 상대·접속 자격을 폐기합니다. 마지막 통신 이후에도 남을 수 있는 임시 정리 도구의 제거 절차를 설계합니다.
8. 앱 부재·관리 등록 제거·클라이언트 정리 근거가 모두 확인된 경우에만 `deleted`로 처리합니다. 삭제된 환경은 기존 설정이 다시 읽혀도 부활하지 않도록 영속 해제 기록을 유지합니다.

연결이 끊긴 환경은 로컬 파일 제거를 실행·검증할 수 없습니다. ‘등록만 숨기기’를 완전 삭제로 표시하지 않으며 `확인 필요`와 남은 항목을 유지합니다. 마지막 응답 유실은 클라이언트 삭제 성공의 증거가 아닙니다. 별도 제한된 검증 경로나 사용자의 현장 제거 확인 절차를 제공하고, 실제 확인 전에는 완료로 바꾸지 않습니다.

같은 삭제 요청을 반복하면 같은 작업을 조회합니다. 외부 삭제 결과가 불확실하면 무조건 다시 삭제하지 않고 실제 상태를 먼저 대조합니다. 중간에 실패한 경우 이미 삭제한 앱을 자동 복구하지 않으며, 확인된 남은 단계만 이어서 실행합니다.

- 사용자가 앱 전용 데이터 함께 삭제를 선택했으므로 데이터 보존 모드 추가 개발은 이번 범위에 포함하지 않습니다. 기본 산정은 현재 지원되는 앱 삭제 동작을 재사용하고 실행 시 데이터 영향을 명시적으로 확인하는 조건입니다.

| A | 범위 확정·작은 실제 연결 검증 | 설치 호스트·프로젝트·실행환경 준비 방식·지속 소유권·데이터 정책을 정합니다. 관리망 도달성과 터널 연결 가능성을 확인합니다. |
| B | 소유권·상태 저장·공통 대상 검사 | 두 사용자·두 환경이 분리되고 삭제 중 환경은 모든 쓰기 경로에서 차단됩니다. 재시작해도 상태가 보존됩니다. |
| C | 등록·클라이언트·WireGuard 연결 | 새 호스트에서 설치 진입점 하나로 등록하고, 재실행·토큰 만료·재부팅을 처리합니다. 터널 연결과 배포 준비를 구분합니다. |
| D | 환경 선택 배포·상태 조회 | 두 OpenStack 환경 중 선택한 곳에만 배포되며 서비스 목록·지표가 같은 환경을 가리킵니다. |
| E | 환경 삭제·클라이언트 제거 | RailShot 앱만 삭제되고 고객 기존 앱은 유지됩니다. 실패 단계·남은 항목·최종 정리 증거가 저장됩니다. |
| F | 통합 검증·배포 인수 | 설치→서비스 두 개 배포→상태 확인→환경 삭제의 실제 흐름을 임시 환경에서 검증합니다. 기존 클라우드 배포도 회귀 검사합니다. |

화면은 B 단계의 데이터 규격이 정해진 뒤 C와 병행할 수 있습니다. 삭제 화면의 모의 구현도 병행할 수 있지만 실제 삭제 인수는 D 이후에 진행합니다. 실제 구현을 시작하면 위 묶음 단위로 코드 검토 요청을 나누되, 연결되지 않은 단계는 사용 가능 기능으로 노출하지 않습니다.

예상 변경 위치는 다음과 같습니다. 저장소 최상위 구조를 바꾸지 않습니다.

## 8. 인수 기준

1. 좌측 구분선·개인 배포환경 관리가 표시되고 키보드 이동, 뒤로 가기, 화면 복귀가 동작합니다.
2. 등록 환경 0개·1개·여러 개, 조회 실패·연결 끊김 상태에서 올바른 선택지와 안내가 표시됩니다. 신규 추가 항목으로 배포 요청을 만들 수 없습니다.
3. 두 사용자가 서로의 환경·서비스·설치 자격·삭제 작업을 조회하거나 조작할 수 없습니다. 소유자 인증 만료와 복구를 검사합니다.
4. 등록 자격 재사용·만료·재발급 후 구형 자격 사용이 차단됩니다. 설치 실패 후 재실행 시 중복 환경·키·서비스가 만들어지지 않습니다.
5. 사설 주소가 같은 두 고객 환경을 등록해도 혼선이 없고, 터널 재연결·서버/고객 호스트 재부팅 뒤 상태가 복구됩니다.
6. 앱 배포는 선택한 환경으로만 전달됩니다. WireGuard 연결만 성공하고 배포 권한·실행환경 준비가 실패한 경우 ‘배포 가능’으로 표시하지 않습니다.
7. 서비스 목록은 실제 등록과 일치하며, 미수집·오래된 메트릭을 정상값으로 꾸미지 않습니다.
8. 임시 환경에 RailShot 서비스 2개와 별도로 만든 고객 서비스 1개를 두고 환경 삭제를 실행합니다. RailShot 서비스만 제거되고 고객 서비스·기반 인프라는 유지됩니다.
9. 배포 진행 중 삭제, 삭제 중 새 배포, 같은 요청 재전송, 서버 재시작, 각 정리 단계 실패를 검사합니다. 불확실한 결과는 완료로 처리하지 않습니다.
10. 클라이언트 전용 파일·서비스·접속키·WireGuard 설정과 서버 연결 등록의 제거를 확인합니다. 공유 패키지·기존 원격접속 설정은 보존합니다.
11. 기존 공용·소유 불명 환경의 삭제는 차단하고, 지워진 환경이 오래된 설정이나 서버 재시작으로 되살아나지 않는지 확인합니다.
12. AWS/GCP 배포·앱 관리·모니터링의 기존 검사를 통과합니다. 자동 검사와 임시 환경 실검증 결과는 구분해서 기록합니다.

이번 계획 작성에서는 코드를 읽고 요구사항·변경 범위를 검토했습니다. 위 인수 검사를 실행하거나 새 기능의 실제 연결 성공을 확인하지 않았습니다.

## 9. 착수 시 정할 항목

확정된 사항은 **RailShot으로 배포한 서비스만 삭제한다는 범위**입니다. 다시 고객 전체 서비스 삭제로 확장하지 않습니다. 아래는 그 범위 안에서 구현을 구체화할 항목입니다.

- 확정: 로그인 없이 장기 소유자 쿠키와 복구키로 소유권을 유지합니다. 복구 시 기존 쿠키와 복구키를 모두 회전합니다.
- 설치 위치·실행환경: 전용 Ubuntu 24.04 관리 호스트와 기존 실행환경 연결/고정 사양 준비 중 첫 지원 경로.
- 확정: 서비스와 앱 전용 영구 데이터를 함께 삭제합니다. 계획 확인 및 delete_data=true 명시 동의가 필요하며 공유·외부 데이터는 제외합니다.
- 관리 호스트에서 외부 WireGuard 통신이 가능한지와 실검증에 사용할 임시 OpenStack 프로젝트.

## 용어

- 워크트리: 같은 Git 저장소에서 별도 브랜치의 파일을 분리해 작업하는 디렉터리입니다.
- 온프레미스: 사용자가 직접 소유하거나 운영하는 인프라입니다.
- API: 화면·클라이언트와 서버가 기능을 주고받는 호출 인터페이스입니다.
- WireGuard: 암호화된 네트워크 연결을 만드는 도구입니다. UDP는 이 연결에 사용하는 통신 방식입니다.
- K3s: 가벼운 Kubernetes 배포판이며, Kubernetes는 컨테이너 서비스를 실행·관리하는 시스템입니다.
- CPU: 중앙처리장치입니다. 메트릭은 사용률·응답 여부 같은 측정값입니다.
- 일회용 등록 자격: 새 클라이언트를 특정 환경에 연결할 때 한 번 사용하는 비밀값입니다.
- 게이트웨이: 고객 환경과 관리 서버 사이의 연결을 중계하는 서버입니다.
- 인수 검증: 요청한 기능이 실제 사용 흐름에서 완료 조건을 만족하는지 확인하는 검사입니다.
